## 本轮行为修正

1. **平台解耦**：发布路径来自项目工作目录或环境配置；签名密钥、信任公钥必须独立提供；无默认生产设备列表。硬件和 APP 白名单进入产品 profile。GK1221 健康日志解析移入适配器。
2. **并发保护**：所有安装、状态写入、激活与恢复共用事务锁，避免安装器删除正在试运行的非确认槽；TRIAL/TRIAL_ARMED 拒绝覆盖。STAGED 只允许更大计数的候选替换。
3. **发行计数**：从每个版本重新从1计数改为同一发行线内持续递增。预留后失败允许空洞；输出与 HTTP 路径为 VERSION-rCOUNTER，避免同版本重发互相覆盖。
4. **状态冗余**：新记录校验正确但字段缺失、重复或 PHASE 无效时尝试另一份；原逻辑只在校验和有效记录之间选最大代数，随后解析失败就结束。
5. **激活默认值**：当前 APP 健康由 warn 改为 enforce；工厂健康旁路由启用改为禁用。需要迁移旁路时必须作为受信设备策略单独配置，不会从旧值默默继承。
6. **签名元数据**：安装器强制 FORMAT_VERSION=2，关键字段必须唯一；安全状态关键字段也拒绝重复。
7. **打包与启动**：拒绝覆盖已有 Bundle/工厂目录；应用文件名与下载器允许范围一致；恢复启动器输出重定向到已声明的 supervisor 日志。健康采样缺失或不新鲜时清零连续成功计数。
8. **双状态损坏恢复**：从有效槽重建时同时恢复 artifact/version/counter，避免重新标成 factory/counter=0；排除已在 quarantine 中记录失败的槽。该修正仍依赖可信本地槽，不提供硬件级防回滚。

## 接入现有板卡的顺序

1. 读取目标板现有 confirmed/pending slot、active/pending counter、rootfs ABI 和存储布局。不要在 TRIAL 或 TRIAL_ARMED 中替换控制程序。
2. 使用匹配目标 libc 和浮点 ABI 的工具链构建三项原生工具。用独立临时构建目录生成覆盖层；显式注入当前受信签名公钥。
3. 结合原 rootfs 打包机制合入覆盖层，在板级准备完成后调用 ota-start。原先已经安装在板上的 bind-mount 控制程序应通过受控维护流程移除或同步，避免旧脚本覆盖新程序。
4. 保留原状态与槽目录；Bundle v2/State v1 不变，无需改写正常状态文件。出厂全新介质用 prepare_factory_image；旧平面 APP 布局通过 ota-migrate-legacy migrate，再验证启动成功后 finalize。现场低空间和旧元数据须在迁移前评估。
5. 按新接口接入业务安全状态和健康日志。新默认策略比原基线严格，不健康的旧 APP 可能无法直接授权，需先完成健康接口或明确配置维护策略。
6. 初始化唯一发布计数源，至少高于设备群中已使用的最大计数；先针对一台测试设备验证，随后扩大范围。

以上是接入步骤，未在本次会话对设备执行。现场网络服务与 PKI 不自动变更。
